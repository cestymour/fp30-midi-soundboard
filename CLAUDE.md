# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

PWA soundboard for live improv theater, used on stage on an Android tablet in Chrome. It drives a Roland FP-30X digital piano over MIDI (USB through Web MIDI, or BLE MIDI through Web Bluetooth), and it also plays audio: one music at a time through a Web Audio effects chain (music tabs), and short sounds that play over everything (sound tabs). Patches and effects go to MIDI channel 4, the channel of the piano's own keyboard sound: a patch there changes what the keys play, so there is no Local Off and no loopback of the notes. Code comments, UI strings, docs and commit messages are in French.

Documentation (`docs/`):

- `usage-scene.md`: how the app is used during a show (who leads the scene, sounds the characters hear versus soundtrack music, the role of the piano, how long a music actually plays). Read it before choosing or presenting sounds and musics.
- `sons.md`: the rules for sounds and musics (which tab, how a tile reads, file names, audio processing and loudness targets) and the state of the files (cut or edited files, musics set aside). Read it before adding, moving or processing a sound.
- `fp30x-midi.md`: what the FP-30X accepts (channel 4, CCs, Roland SysEx).
- `todo.md`, `bugs.md`, `checklist.md`: see the working rules below. `CHANGELOG.md` (repo root) has the release notes.
- `DOC_FP30X/`: Roland's manuals and MIDI implementation.

Production: https://cestymour.github.io/fp30-midi-soundboard/ (GitHub Pages). History: the app was plain JS until 1.6.4 (tag `v1-vanilla`), then rewritten with Vite, TypeScript and Svelte without changing its behaviour (1.7.0).

## Working rules

- **Browser support**: everything must work, and look the same, on **Chrome 106** (106.0.5249.126, the stage tablet, Android 6.0, which cannot update Chrome). Before using a CSS or JS feature, check that it exists in Chrome 106; if it does not, add a fallback and check it. Known cases:
  - `color-mix()` (Chrome 111): keep writing it in the sources. At build time, the PostCSS plugin `tools/color-mix-compat.ts` (in `vite.config.ts`) rewrites each `color-mix(in srgb, …)` into `rgb(calc(…))` / `rgba(…)` on channel variables (`--name-r`, `-g`, `-b`, `-a`). A color variable declared in CSS as hex gets its channels automatically. A color variable set by script (`style:--panel-accent`, `style:--cat-accent`) must set its channels too, with `colorChannels()` (`src/ui/color-channels.ts`). An unsupported form (named color, another color space) fails the build. A fallback declaration placed before a `color-mix()` with `var()` does not work: the browser keeps `color-mix()` and drops it when computing values (bug n° 26).
  - `dvh` (Chrome 108): put a `vh` declaration before it.
  - Available: `:has()` and container queries (`cqh`, `cqw`) since Chrome 105.
  - To check on a real Chrome 106 without the tablet: Chromium snapshot 1036838 (106.0.5249.0), `https://storage.googleapis.com/chromium-browser-snapshots/Win_x64/1036838/chrome-win.zip`, unzipped outside the repo. The simplest check is the regression tool on it: `CHROMIUM_PATH=<path>/chrome-win/chrome.exe npm run regression` (Playwright drives it fine). Run by hand, use `--headless` (not `--headless=new`) and a fresh `--user-data-dir` (the Service Worker of a reused profile serves the previous build).
  - Build target: `vite.config.ts` sets `build.target` to Vite 6's former default (`chrome87`, `safari14`…), since Vite 8 targets Chrome 107+ by default, and `build.cssMinify: 'esbuild'`, since Lightning CSS (Vite 8's default) rewrites media queries and gradients and Chrome 106 renders the slider thumbs slightly differently. Keep both.
- **Production**: every push to `main` deploys, and the app is used on stage. Never merge into or push `main` without the user's explicit approval. The user does the `git push` themselves unless they explicitly allow it for one task.
- Small commits in French, in the style of the history, one commit per topic (one per bug fix).
- **To-do**: `docs/todo.md` lists the user's planned ideas and features (priorities, presets, new sounds, looper for 2.0, themes tab) and the technical debt. Add new ideas there; when one is done, remove it and describe it in `CHANGELOG.md`.
- **Bugs**: a bug found along the way goes into `docs/bugs.md` first, under « Ouverts », with its diagnosis (scenario, cause, consequences, suggested fix) and the next free number. The user decides whether and when to fix it; don't fix it in passing. Once fixed, it moves to the « Fermés » table in one line. Comments and tests refer to bugs by number (« bug n° 11 »).
- **Comments** describe the code as it is and why, not its history (no « désormais », « ancien », « depuis la 1.x »): history belongs in commits and `CHANGELOG.md`.
- **Node**: Node 24 (`.nvmrc`). The user develops on Windows, where Node 24 is installed directly (no nvm): npm commands run as is, in Git Bash or PowerShell. On Linux with nvm, run `source ~/.nvm/nvm.sh && nvm use` first and never change the nvm default.
- **Release**: bump `version` in `package.json` (see below), add the version's section at the top of `CHANGELOG.md` (`## X.Y.Z — date`, in French, written for the user of the app: new features, fixes, things to know, known limits, what to check on the tablet), run `npm run typecheck`, `npm test`, `npm run build` and `npm run regression`, check what changed on the tablet with `docs/checklist.md`, then tag the released commit `vX.Y.Z` (annotated) and push the tag: the regression tool uses the latest tag as its reference.

## Commands

Vite build, TypeScript (`strict`) in ES modules, Svelte 5 (runes) for the UI. Vitest for unit tests, no linter.

- Node version is pinned in `.nvmrc` (24 LTS; `vite-plugin-pwa` needs Node ≥ 20). See the Node rule above.
- `npm install` once, then `npm run dev` (dev server on http://localhost:5173/, no Service Worker).
- `npm run typecheck` runs `svelte-check --fail-on-warnings` on the app (`tsconfig.json`, DOM lib, `.ts` and `.svelte`), then `tsc` on `tsconfig.sw.json` (`src/sw.ts`, WebWorker lib) and `tsconfig.node.json` (`vite.config.ts`). Vite itself does not typecheck. Svelte warnings (unused CSS selector, a11y) fail the check: fix them, or add a `svelte-ignore` comment with the reason.
- `npm test` runs Vitest once (`*.test.ts` next to the code).
- `npm run build` builds to `dist/`, and `npm run preview` serves the build with the Service Worker (http://localhost:4173/). `vite.config.ts` uses `base: './'` because production is served under `/fp30-midi-soundboard/`.
- Deploy: every push to `main` runs `npm ci`, `npm run typecheck`, `npm test` and `npm run build`, then publishes `dist/` to GitHub Pages (`.github/workflows/deploy.yml`). The Pages source must stay on « GitHub Actions » (with « Deploy from a branch », GitHub's own job overwrites the site with the raw sources). `gh` is not installed: follow a run through the public API (`https://api.github.com/repos/cestymour/fp30-midi-soundboard/actions/runs`) and check the site with `curl`.

## Releasing / cache invalidation

Nothing to bump by hand for caching. `src/sw.ts` is a Workbox Service Worker built by `vite-plugin-pwa` (`injectManifest`) and published as `sw.js` at the site root. The precache list and file revisions are generated at build time (HTML, JS, CSS, fonts, icons, `manifest.json`). The SW calls `skipWaiting()` and `clientsClaim()`: a new version installs in the background at launch and shows at the next launch. The settings popup's « Mettre à jour l'application » button (`src/app-update.ts`) skips that wait: `registration.update()`, wait for the new SW to be active, then reload; nothing is reloaded if the site does not answer (offline). It never unregisters the SW and never clears a cache.

- Content hashes: at build time, `tools/asset-hashes.ts` hashes every file of `public/sounds/` and `public/images/` (injected as `__ASSET_HASHES__`, see `vite.config.ts`; empty in dev and tests). Every read of a sound or image goes through `assetUrl()` (`src/asset-url.ts`), which appends `?v=<hash>`: a file replaced under the same name gets a new URL, so the tablet fetches it. Any new place that reads a sound or image must use `assetUrl()`.
- Sounds (`/sounds/`): `CacheFirst` in the stable, unversioned cache `impro-audio`. On a miss the whole file is fetched without the `Range` header (a 206 can't be cached), and `RangeRequestsPlugin` then serves `<audio>` range requests from the cache. Offline, when the requested version is not cached, the SW serves another version of the same path left in the cache (`ignoreSearch`, sliced for a `Range` request).
- Images (`/images/`): `CacheFirst` in `impro-images`, with the same offline fallback.
- Fonts (Rajdhani, IBM Plex Mono) come from the `@fontsource/*` packages, imported in `src/main.ts` (same weights as the former Google Fonts link), and are precached (`woff2` in `globPatterns`). The SW deletes the former Google Fonts caches (`impro-fonts-css`, `impro-fonts`) on activation.
- Cache names shared by the SW and the page are in `src/cache-names.ts`.
- `src/offline.ts`: `requestPersistentStorage()` (called at startup in `src/main.ts`, so Chrome does not evict the sound cache), and the settings popup's « Télécharger tous les sons », which fetches every sound and cover image of the config that is not cached yet and puts it in `impro-audio` / `impro-images` from the page, under the URL `<audio>` requests (hash included). Then, only if every download succeeded, it deletes the cache entries that match no URL of the config (removed or renamed file, old hash) and reports the space freed. The popup shows the button while files are missing or obsolete entries remain (« Libérer la place des anciens fichiers » when nothing is missing).
- The SW is registered in `src/main.ts`, in production builds only.

The version shown in the settings popup comes from `package.json` (`version`), injected at build time as `__APP_VERSION__` (see `vite.config.ts`). Bump it for each release so you can tell on the tablet which version is running.

For a CSS-only change, `npm run regression:styles -- <reference build>` compares the computed style of every element (and `::before` / `::after`) between two builds, in about twenty UI states and at every media query breakpoint. See its README.
- `docs/checklist.md`: the manual checklist on the tablet, with the real piano, and how to serve the app to the tablet (`adb reverse`) or to a browser on the Windows host.

## Architecture

Entry point: `index.html` only holds `<div id="app">`. It loads `src/main.ts`, which imports the global CSS, subscribes the UI state to the engines' events, mounts `src/App.svelte`, then starts Wake Lock (`src/wake-lock.ts`), Bluetooth, Web MIDI and the Service Worker. Every dependency is an explicit `import`. There are no shared globals besides browser APIs.

- `src/sw.ts`: the Service Worker (see above).
- `public/`: static files copied as-is to the site root: `sounds/`, `images/`, icons, `manifest.json`. Config paths such as `file: 'sounds/x.mp3'` and `img: 'images/films/x.jpg'` are relative to the page, so they work both in dev and under the GitHub Pages sub-path.
- `src/types.ts`: shared types: config schema (`MidiTab`, `MidiItem`, `AudioTab`, `AudioItem`, `Category`), FX controls and presets (`FxControl`, `FxPreset`, `MidiFxKey`, `AudioFxKey`).
- `src/state.svelte.ts`: the shared `STATE` object, a class with `$state` fields (`AppState`). Objects compared by identity or owned by browser APIs (MIDI ports, BLE, tracks, the current `AudioItem`) use `$state.raw`, so they are never proxied.
- `src/config/tabs.ts`: `getMidiTabs()` / `getAudioTabs()`. Components never read `MIDI_TABS` / `AUDIO_TABS` directly: these functions are the single place to apply user preferences later (hidden tiles, order).
- `src/config/*.config.ts`: pure data exports (`MIDI_TABS`, `AUDIO_TABS`, `MIDI_FX_PRESETS`, `AUDIO_FX_PRESETS`). `config.test.ts` checks that every `id` is unique among its siblings.
- `src/events.ts`: `createEmitter()`, the small typed event emitter the engines use to notify the UI.

Engines (`src/midi/`, `src/audio/`, `src/fx/`) never touch the DOM and never import `src/ui/` or the Svelte components; the UI subscribes to their events. Keep it that way (the remaining browser APIs there are Web MIDI, Web Bluetooth, Web Audio, the `<audio>` element used for playback, and `requestAnimationFrame`).

- `src/midi/midi.ts`: sending only. `sendMidi()` routes to the USB `STATE.midiOutput` when present, otherwise to BLE `STATE.bt`; `buildInstrumentPatchMessages()` (`pc` 1-based → 0-based), patch, volume, all-notes-off, and Roland SysEx (`buildRolandDt1()`: remote control, sent at every connection, and Ambience, which is the keyboard sound's reverb, since channel 4 ignores CC91). SysEx goes through `sendMidi()` too: over USB only if Web MIDI access was granted with `sysex: true` (`initWebMidi()` asks for it, falls back without). Only BLE messages are logged to the console (`MIDI OUT (BT)`).
- `src/midi/connection.ts`: USB (Web MIDI) and BLE connection handling, `selectMidiConnection()`, `midiConnectionEvents` (`status`, `selection`, `outputs`, `connected`). At every connection (USB, BLE, automatic BLE reconnection) it sends the Roland remote control then the volume, and emits `connected`, on which `bindMidiConnectionUI()` resends the highlighted instrument and every MIDI FX value (`sendAllMidiFx()`). A newer choice supersedes a BLE connection still in progress (`selectionId`). `autoConnectUsbPiano()` connects to the first USB output whose name contains « piano » (the FP-30X shows up as « Roland Digital Piano ») when no connection is active: on the first Web MIDI access, then when a piano output appears; an unplugged output (`state === 'disconnected'`) is dropped and the badge goes back to « Non connecté ».
- `src/midi/bluetoothMIDI.ts`: the `BluetoothMIDI` class (a GATT write queue; `buildBleMidiPackets()` wraps each message, SysEx included, into BLE MIDI packets). Incoming notes are only decoded and logged (`MIDI IN (BT)`). The connection logic follows chord-finder-midi's controller: every action bumps `#attempt` so stale async work gives up, `#target` is the wanted device, and a GATT link is never left open with nobody listening. An unrequested disconnect starts an automatic reconnection to the same device (20 s, status `reconnecting`, then `lost`). The last device stays known (`knownDeviceName`, saved in `localStorage`): `reconnect()` reconnects without the picker (no user gesture needed), and on launch `restore()` finds it again through `navigator.bluetooth.getDevices()` where the browser allows it (not Edge on Windows by default, checked 2026-11-05; untested on the tablet). Without `getDevices`, the piano is still offered under its saved name (`localStorage`), and choosing it opens the picker filtered on that name: a user gesture is required there. Nothing ever connects on its own at launch (user's choice: opening the app on a second device must not take the piano away). The connection lists then offer « ᛒ <name> » (reconnect) and « Autre appareil Bluetooth… » (full picker). `STATE.btStatus` / `btError` mirror the status for the badge.
- `src/midi/ble-midi-parser.ts`: BLE MIDI packet parser, an ES port of the `packets` part of skratchdot's `ble-midi` (the npm package itself is a Node CLI with native deps and is unusable in the browser).
- Audio tabs are of two kinds (`kind` in the config, `AudioTabKind`): **music tabs** (`music`: Ambiances, Musiques, Films) share a single music track, with fades, the audio FX and the music volume; **sound tabs** (`sounds`: Animaux, Bruits) play short sounds over everything else, with no fade, no FX and their own volume.
- `src/audio/audio-engine.ts`: the `AudioEngine` class (a single Web Audio graph: EQ → filters → delay/reverb → master → limiter; delay and reverb only get the signal while their mix is above 0, so Chrome idles them) and `MediaElementTrack`, exported as `AudioEngineAPI`. Every track must end with `dispose()`, which disconnects it from the graph. Sounds go through a separate gain, `soundsBus`, connected straight to the limiter (no FX, no music volume): `getSoundsOutput()`, `setSoundsVolume()`. A track created with route `'transition'` (`createTrack(src, 'transition')`) goes through `transitionBus`, also straight to the limiter: no FX, no speed, its own volume (`setTransitionVolume()`) and its own optional effects chain (`setTransitionEffects()`, off by default, crossfaded on toggle); its fades act on its own output gain (`transitionOut`, after its effects chain, so a fade-out also cuts the reverb tail), not on the master, and the engine's loops over tracks (master volume, speed, reset) skip it.
- `src/audio/playback.ts`: music only. `playSound(item)`, `stopSound`, `togglePlayPause`, `seekToRatio`, `setMusicVolume`, fades and the progress loop; `playbackEvents` (`play`, `stop`, `pause`, `resume`, `progress-start`, `progress`, `missing`). The current music is `STATE.currentSoundItem` (an `AudioItem`, not a button). One fade at a time: a new fade cancels the running one. Switching music cuts the previous one dead, on purpose (the next one must start at once, with its own fade-in).
- `src/audio/sounds.ts`: sounds of the sound tabs. `playOneShot(item)` decodes the file into an `AudioBuffer` on its first click (`fetch`, so it is read from the offline cache through the SW), keeps decoded sounds in memory within a 50 MB budget (least recently played forgotten first), and starts a new `AudioBufferSourceNode` on every click, even for a sound already playing. At most 8 voices: the 9th takes the place of the oldest (cut with a few-millisecond ramp). `stopAllSounds()` (the ⏹ button and the emergency stop) also cancels sounds still decoding. `setSoundVolume`, `getSoundProgress(item)` (latest voice of the item), `soundEvents` (`start`, `end` with the item's remaining voices, `progress`, `missing`). `STATE.soundVoices` counts the voices.
- `src/audio/transition.ts`: the transition music (header button). One music for the whole show (`src/config/transition.config.ts`, `TRANSITION_MUSICS`, through `getTransitionMusics()`; files in `public/sounds/transitions/`), played through `playSound(item, { route: 'transition', startAt })`, so it is the single music like any other. Key moments: 0 is `start` (opening of the show), 1, 2… are `restarts`, played in turn after each improv (0, 1, 2, 3, 1, 2, 3…). `getNextMoment()` is the successor of the last moment played (`STATE.transitionLastMoment`, even one played out of order), or 0 when another music was picked or the last launch is older than 6 hours (`RESTART_WINDOW_MS`). `launchTransition(now, moment = getNextMoment())` first stops everything like the emergency stop (`stopAllSounds()`, `sendEmergencyStopMidi()`; `playSound` cuts the music); `stopTransition()` fades it out. Choice, last launch, last moment, volume and the « reset volume to 100 % when the popup opens » switch (`setTransitionResetVolume()`, applied by `openTransitionPopup()`) and the « Clarté Studio » button (`setTransitionClarity()`: the `crystal` audio FX preset, read through `getClarityEffects()`, applied by the engine's `setTransitionEffects()` to the transition's own small chain: EQ, filters, reverb; the music FX chain is untouched) are in `STATE.transition*` and saved in `localStorage`. `playSound`'s fade-in targets 1 for this route (the volume is on the bus), and `setMusicVolume()` leaves it alone.
- `src/audio/timing.ts`: pure time helpers (playback range from `start`/`end`, progress, seek time, `formatTime`).
- `src/fx/fx-presets.ts`: the single, pure preset logic shared by both FX popups (target values, clamp, active preset inference, neutral checks, interpolation). `src/fx/fx-animation.ts` animates values towards targets.
- `src/fx/midi-fx.ts`, `src/fx/audio-fx.ts`: the `*_FX_CONTROLS` arrays, `MIDI_FX_STATE`, and how a value is applied.

UI (Svelte 5). The `*.svelte.ts` modules hold the UI state in runes and the logic that is not tied to one component:

- `src/ui/fx-overlay.svelte.ts`: `FxOverlayController`, the state and logic of one FX popup (values, active preset, layout over the active grid, animations). `src/ui/fx-overlays.svelte.ts` creates the MIDI and audio controllers with only what differs (ids, data attributes, settings source, audio low-pass fix-up), plus `fxToolbar` (the Effets/Reset buttons state: one Reset light per FX type). Each panel's Reset only resets its own FX popup (piano on MIDI tabs, sounds on audio tabs).
- `src/ui/transport.svelte.ts`: per-sound button state (`getSoundButtonState(item)`: progress, reset to 0 when the sound stops, transition, missing, `playing` for sound tabs) and the transport bar text and fill; `bindPlaybackUI()` subscribes to `playbackEvents`, `bindSoundsUI()` to `soundEvents`.
- `src/ui/midi-ui.svelte.ts`: connection selects (one per MIDI panel) and the active instrument; `bindMidiConnectionUI()` subscribes to `midiConnectionEvents`.
- `src/ui/layout.svelte.ts`: active tab, orientation, `activateTab()`, and the button height equalization.
- `src/ui/transition.svelte.ts`: the transition popup state; only the header button opens it, stopping the transition music leaves it open, and `bindTransitionUI()` closes it when a music tab's music starts. Its size never changes with the state (fixed-height rows, the fallback button hidden with `visibility`).

Components:

- `src/App.svelte`: header (transition button, tabs, settings button), one panel per tab, transition popup, settings popup, the two FX popups.
- `src/ui/FxOverlay.svelte`: the single generic FX popup, driven by its controller.
- `src/ui/components/`: `TabNav`, `Panel` (frame and controls bar shared by both panel types), `MidiPanel`, `AudioPanel` (music tabs: transport, Effets/Reset, emergency stop, music volume; sound tabs: `StopSoundsButton`, emergency stop, sound volume), `SoundButton` (music: stop square while playing; sounds: « repeat » double arrow, each click relaunches), `Transport` (play/pause, seek drag, time), `FxToolbar` (Effets/Reset), `VolumeControl` (its icon is derived from the shared volume, so it matches on every panel of the same kind), `EmergencyStopButton` (piano, music and sounds), `StopSoundsButton`, `TransitionButton` (top-left square of the header, mirror of the settings button: 🎉 opens the popup; popup open, a play triangle that launches the planned moment, so a double tap opens and plays; while the transition music plays, a stop square with the progress fill that stops it, leaving the popup open; a ▶/■ click within 0.6 s of the previous one is ignored, so a double tap never plays then stops), `TransitionPopup` (below the header, always the same size: music choice, progress with a marker per moment, a row of moment buttons 0, 1, 2… with the planned one coloured and wider, replaced by a big « Arrêter » while playing, a one-line caption, volume, the reset-volume switch and the « Clarté Studio » toggle), `CategoryTitle`, `SettingsPopup` (⚙ button, sections from top to bottom: Écran with the highlighted « Plein écran » button and the Wake Lock, Hors ligne with cached sounds and images, storage, Service Worker and « Télécharger tous les sons », Application with the version and « Mettre à jour l'application »; each status is a row with a green, orange or grey dot).

Styles: `src/css/global.css` holds the variables, reset, page layout and the `.vol-slider` range input shared by the volume controls and the FX popups. Everything else is scoped in the components. Each rule family stays in a single component, in cascade order (all `.sound-btn` rules are in `SoundButton.svelte`, including the animals-grid and column variants, through `:global(.animals-grid) .sound-btn`), so the cascade order is kept: Svelte adds the same specificity (one class) to every scoped rule.

### Tabs

The UI is generated entirely from `MIDI_TABS` / `AUDIO_TABS` (through `src/config/tabs.ts`): tab → categories → items. `{#each}` blocks are keyed by `id`. Tabs, categories and items all carry a required `id`: a short slug, unique among its siblings (tab ids are unique across MIDI and audio tabs), that must never change once set, even if the label, file or patch changes. Commented-out config entries keep their id too. New ids follow the same rule (Films tab items use the cover image file name). MIDI items carry `pc` (1-based, sent as `pc - 1`), `msb` (CC0) and `lsb` (CC32). Audio items carry `file` and optionally `img`, `start`, `end`, `catClass`. Audio tabs carry `kind` (`'sounds'` or `'music'`). Tabs have no color of their own: the accent comes from the kind of tab (`TAB_ACCENTS` in `src/config/tabs.ts`: MIDI, sounds, music). `noFade` only applies to music tabs. Tab-level options `cols` and `gridType: 'animals'` change the grid layout. The README documents the full config schema.

### FX overlays

Both popups (MIDI and audio) are the same `FxOverlay.svelte` component, each driven by an `FxOverlayController`. Only `src/ui/fx-overlays.svelte.ts` holds what differs.

- Each popup is driven by a `*_FX_CONTROLS` array. Each control has `key`, `min`/`max`/`step`, `neutral`, `read(settings)`, `apply(value)` and `formatValue`.
- A preset's `values` only lists the controls it changes. Every other control falls back to its `neutral` value, not to the slider's current position. `values: null` is the reset preset.
- The active preset is inferred from the current slider values (`inferActiveFxPresetKey`), so the highlight comes back after a tab switch or after the popup is closed and reopened.
- MIDI FX state is whatever the app last sent (`MIDI_FX_STATE`). It is never read back from the piano. Audio FX state is read from `AudioEngineAPI.getCurrentSettings()`.

### Layout

Button heights are equalized in JS (`equalizeMidiButtons` / `equalizeAudioButtons` in `src/ui/layout.svelte.ts`, run on tab change, orientation change and by a `ResizeObserver`): they measure the rendered grid, and a pure CSS version would not render identically. In portrait, `MidiPanel.svelte` redistributes the categories over 2 columns. The target device is an ~11" landscape/portrait tablet, so check both orientations.
